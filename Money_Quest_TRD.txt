1. System Architecture Overview
1.1 Architecture Philosophy
Money Quest Adventure is built on a microservices architecture designed for global scalability, low-latency delivery to learners worldwide, and independent deployability of each platform subsystem. The architecture prioritises educational continuity - if any non-core service degrades, the primary learning experience remains fully functional.
1.2 High-Level Architecture
ARCHITECTURE PATTERN
Client-Side Rendering (CSR) React SPA with a Node.js/Express BFF (Backend for Frontend), PostgreSQL primary database, Redis caching layer, S3 media storage, CloudFront CDN, and a separate Python-based AI Question Generation microservice. Event-driven inter-service communication via AWS SQS/SNS.

5. Simulation Engine Design
5.1 Coin Recognition Engine
The Coin Recognition Engine uses Pixi.js for hardware-accelerated 2D rendering of interactive coin sprites:
ENGINE SPECIFICATION
Pixi.js 8.x WebGL renderer; canvas fallback for older browsers. Target: 60fps on mid-range Android tablets (2022+). Coin physics: Matter.js 0.19.x for drag-and-drop physics simulation. Texture atlases: one per denomination group (1-5 cent coins, 10-50 cent coins, 1 dollar+). Each atlas max 2048x2048px.
Coin Sprite States: Idle (gentle rotation 1 RPM), Hover (scale 1.15 + shadow appear, 200ms), Dragging (scale 1.2 + tilt 5 degrees + shadow offset), Dropped (bounce physics, settle animation), Selected (gold ring highlight + pulse)
Interaction Events: pointerdown, pointermove, pointerup, pointerover, pointerout - all handled through Pixi's InteractionManager
Collision Detection: Matter.js compound bodies per coin shape; snap zones use rectangular trigger regions
Performance Budget: Maximum 15 coin sprites simultaneously active; LOD reduction at >10 sprites
5.2 Money Counting Engine
The counting engine manages the running total calculation, visual feedback, and narration triggers:
interface CountingState {
  collectedCoins: Coin[];          // Array of coins in the bag/tray
  runningTotal: number;            // Current total in cents
  targetAmount: number | null;     // Target (null for open counting)
  countingStep: number;            // Current step in guided counting
  narrationTimestamp: number;      // Current position in audio file
  isComplete: boolean;             // Has target been reached?
}
Skip counting assistance: When counting a set of same-denomination coins, the engine highlights each coin sequentially with a count-out animation, triggering the narrator to say the running total at each step. Students can toggle between "count-all" mode and "skip-count" mode via an accessibility toggle.

6.2 Audio Engine Implementation
The Audio Engine is built on Howler.js with a custom synchronization layer:
Sprite system: All UI sound effects bundled into a single Howler sprite for minimal HTTP requests
Narration queue: FIFO queue manages sequential narration playback across screen transitions
Timestamp polling: A 50ms setInterval polls Howler's seek() position and fires events when timestamps are crossed
State persistence: Current narration position persisted in sessionStorage; auto-resumes on browser reload
Speed control: Howler's rate parameter adjusts playback speed (0.75, 1.0, 1.25) without pitch shift
Interrupt handling: onvisibilitychange pauses narration; onblur reduces ambient audio to 20% volume

7. Dynamic Question Generation Engine
7.1 Engine Overview
The Question Generation Engine is a dedicated Python/FastAPI microservice that produces unlimited, curriculum-aligned, difficulty-scaled money questions with zero repetition within a session:
ENGINE PRINCIPLE
No hardcoded question banks. Every question is algorithmically assembled from parameterized templates, randomized values within curriculum-appropriate ranges, and contextual shopping scenarios pulled from a scenario vocabulary database. Anti-repetition logic prevents the same combination of values appearing twice in a 24-hour period per student.
7.2 Question Type Specifications
Question Type
Algorithm Description
Parameters
Coin Counting
Select N coins from denomination set D; compute total; generate distractors within +-20% of correct answer
N: 1-12 coins; D: varies by level; Distractors: 3; Format: multiple choice or numeric input
Note Counting
Select M notes from denomination set N; compute total; ensure total does not exceed level maximum
M: 1-6 notes; N: $1-$20; Max total: $50; Distractors: 3
Mixed Money
Combine K coins and J notes; compute combined total; optionally ask for minimum denomination count
K: 1-8 coins; J: 1-3 notes; Difficulty modifier on denomination variety
Compare Money
Generate two amounts A and B with controlled delta D; student identifies >, <, or = relationship
A, B range: $0.01-$9.99; Delta D: small (0-$0.25), medium (0-$1.00), large (0-$5.00)
Exact Payment
Generate item price P; student selects coins/notes to make exact amount P
P range: $0.05-$9.95 (steps of $0.05); Available denominations vary by level
Find Change
Generate item price P and tender T where T > P; compute change C = T - P
P: $0.25-$9.75; T: next round denomination above P; C: $0.25-$5.00
Shopping Total
Select 2-3 items from scenario vocabulary; compute total; may include find-change sub-problem
Items: 2-3; Price range per item: $0.50-$5.00; Total cap: $15.00
Word Problem
Assemble narrative from subject+action+amount templates; embed mathematical operation
Subjects: 20 child-relevant nouns; Actions: buy, receive, save, spend; Operation: add or subtract
Adaptive Challenge
Same as above but with parameters scaled 1.5x beyond current mastery level; used for challenge mode only
Triggered when 5 consecutive correct answers at current level; auto-retreats on failure
7.3 Anti-Repetition Algorithm
The anti-repetition system ensures diverse question experiences:
Session hash: A hash of the last 20 questions' parameter combinations is stored in Redis per student per session
Candidate validation: Each generated question candidate is hashed; if hash exists in session, regenerate
Value spacing: For numeric questions, new values must differ by at least 15% from the last 3 questions of the same type
Scenario rotation: Shopping scenario subjects rotate through a 50-item vocabulary list; no subject repeats within 10 questions
Daily reset: Session hashes expire at midnight UTC; fresh diversity guaranteed each day

Classroom leaderboards: Redis sorted sets per classroom; updated in real-time on XP award
Global leaderboards: Weekly reset; sharded by grade level to ensure fair comparison

11. Worksheet Generation System
11.1 Generation Architecture
Worksheets are generated server-side using Puppeteer rendering a Handlebars HTML template, then uploaded to S3 for persistent download access:
Student completes lesson -> POST /api/worksheets/generate queued via BullMQ
Worker dequeues job; calls Question Engine for 10-12 dynamically generated questions
Handlebars template populated with questions, student name, date, chapter branding, and answer key
Puppeteer renders template to PDF with print-optimized CSS (Helvetica font, grey-scale safe, 1cm margins)
PDF uploaded to S3 at students/{student_id}/worksheets/{lesson_id}/{timestamp}.pdf
Answer key uploaded separately at same path with _answers suffix
Database record created; student, parent, and teacher receive download notification

14. Security Requirements
14.1 Authentication & Authorization
Student accounts: Parent-created with PIN-based login (4-digit numeric PIN for young children); optional Google/Apple SSO for parent-linked login
Parent accounts: Email + password with bcrypt (cost factor 12); MFA available via TOTP
Teacher accounts: Email + password with institutional SSO support (Google Workspace, Microsoft 365)
JWT Strategy: Short-lived access tokens (15min); long-lived refresh tokens (30 days) stored HTTP-only cookies
Authorization: Role-based access control (RBAC) with roles: student, parent, teacher, admin; resource ownership validation on every request
14.2 Data Protection & Privacy
COPPA Compliance: No collection of personal information from children under 13 without verifiable parental consent; minimal data collection principle applied throughout
GDPR-K Compliance: Right to access, right to deletion, data portability for all student data; consent management via parent account
Data Minimization: Student profiles contain only: display name, grade, region, progress data; no real names required for students
Encryption at Rest: All database fields containing PII encrypted using AES-256; S3 server-side encryption enabled
Encryption in Transit: TLS 1.3 minimum for all API communication; HTTP Strict Transport Security (HSTS) headers
API Security: Rate limiting per IP (100 req/min) and per authenticated user (60 req/min); WAF rules via AWS WAF
Content Security Policy: Strict CSP headers preventing XSS; no inline scripts; nonce-based script authorization
Dependency Security: Automated Snyk scanning in CI pipeline; zero critical vulnerabilities policy for production deployment
